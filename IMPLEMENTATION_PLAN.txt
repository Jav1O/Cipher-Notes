2. DECISIONES CRIPTOGRAFICAS APROBADAS
======================================================================

AUTENTICACION
- bcrypt.hashpw() + bcrypt.gensalt() para almacenar el verificador.
- bcrypt.checkpw() para validar login.
- Coste inicial propuesto: 12. Registrar el coste realmente utilizado.
- Usar contrasenas UTF-8, sin recortes silenciosos; bcrypt admite como
  maximo 72 bytes de entrada, por lo que el registro debera rechazar
  longitudes superiores (tambien validar longitud minima definida).
- Nunca almacenar contrasenas en texto claro ni usar SHA-256 simple.

DERIVACION DE LA CLAVE QUE PROTEGE LOS SECRETOS (KEK)
- PBKDF2HMAC con SHA-256, sal aleatoria INDEPENDIENTE de bcrypt,
  longitud de salida 32 bytes.
- Sal sugerida de 16 bytes (os.urandom(16)).
- Parametro inicial de referencia: 600000 iteraciones; comprobar el
  rendimiento real y registrar el valor definitivo en la memoria.
- La KEK se deriva de la contrasena introducida en cada login.
- Ni la contrasena ni la KEK se guardan en la base de datos.

CIFRADO DE NOTAS Y DE CLAVES
- AESGCM de cryptography con claves de 256 bits.
- Nonce aleatorio nuevo de 12 bytes para CADA operacion AES-GCM.
- AESGCM.encrypt devuelve ciphertext y tag juntos. Guardarlos juntos.
- Usar AAD determinista, definido en la seccion 5.
- No reutilizar un nonce bajo la misma clave. Para notas, imponer una
  restriccion UNIQUE(owner_id, nonce) y reintentar ante colision.
- Las claves de notas DEK seran aleatorias (AESGCM.generate_key(256)).
- No dejar claves AES incrustadas en el codigo o en un .env.

FIRMA DIGITAL
- RSA, 2048 bits y exponente publico 65537, conforme a la propuesta.
- RSA-PSS con MGF1(SHA-256), SHA-256 y salt_length=PSS.MAX_LENGTH
  (parametros explicitos e identicos al firmar y verificar).
- Firmar los bytes canonicos del registro de nota cifrada, no una
  concatenacion ambigua de cadenas ni solamente el texto del titulo.
- Clave privada serializada como PKCS8 DER y protegida con AES-GCM
  mediante la KEK; nunca persistir la privada DER sin cifrar.
- Clave publica serializada como SubjectPublicKeyInfo DER; la BD local
  vincula esta clave a la cuenta, NO equivale a un certificado X.509.

POR QUE ESTOS METODOS
- bcrypt y PBKDF: Practica 1 (hashes y contrasenas), ejercicio 4.
- AES-GCM: Practica 2, ejercicio 5, y modulo M4.
- RSA y SHA-256: Practica 3; PSS es la adaptacion segura del esquema
  de firma RSA, NO el padding de firma copiado del ejemplo inicial.
- Claves publicas e identidad: Practica 4 y modulo M8.
- AES-GCM satisface cifrado + integridad/autenticidad. No se requiere
  HMAC independiente para este alcance. RSA-PSS es requisito aparte.

4. MODELO DE DATOS Y PERSISTENCIA (CONTRATO)
======================================================================

Identificadores:
- user_id y note_id: uuid.uuid4().hex (32 caracteres) generados por
  la aplicacion. Son identificadores, NO claves criptograficas.
- username: entre 3 y 32 caracteres ASCII [a-zA-Z0-9_], convertido
  a minusculas para comprobar unicidad coherente.
- Version inicial del formato de notas: integer 1.
- Todos los binarios van en columnas SQLite BLOB (no Base64 en BD).

TABLA users
    id TEXT PRIMARY KEY
    username TEXT NOT NULL UNIQUE
    password_hash BLOB NOT NULL                -- bcrypt
    kdf_salt BLOB NOT NULL                    -- PBKDF2
    kdf_iterations INTEGER NOT NULL
    dek_nonce BLOB NOT NULL                   -- wrap AES-GCM
    encrypted_dek BLOB NOT NULL               -- ciphertext+tag
    rsa_nonce BLOB NOT NULL                   -- wrap AES-GCM
    encrypted_private_key BLOB NOT NULL       -- PKCS8 DER cifrado+tag
    public_key_der BLOB NOT NULL              -- SPKI DER

TABLA notes
    id TEXT PRIMARY KEY
    owner_id TEXT NOT NULL REFERENCES users(id)
    format_version INTEGER NOT NULL
    nonce BLOB NOT NULL                       -- 12 bytes
    ciphertext BLOB NOT NULL                  -- contenido+tag
    signature BLOB NOT NULL                   -- RSA-PSS
    UNIQUE(owner_id, nonce)

- Habilitar PRAGMA foreign_keys = ON en cada conexion SQLite.
- Crear indices basicos en notes(owner_id).
- Usar consultas SQL parametrizadas y transacciones.
- SELECT de nota siempre restringido por id Y owner_id de la sesion.
- No guardar titulo ni cuerpo en claro en ninguna columna.
- No guardar claves DEK, KEK ni privadas RSA sin cifrar.
- Mantener la creacion de usuario y de sus claves en una sola
  transaccion, o revertir completamente ante cualquier error.
- Las claves envueltas se distinguen por su AAD de proposito (ver 5).

======================================================================
5. FORMATO CANONICO Y CONTRATOS DE SEGURIDAD
======================================================================

TODOS LOS MODULOS DEBEN USAR EL MISMO FORMATO.
formats.py sera la UNICA fuente de verdad para construir estos bytes.

Regla de serializacion canonica:
    json.dumps(obj, sort_keys=True, separators=(',', ':'),
               ensure_ascii=True).encode('utf-8')
- Claves JSON exactas y tipos controlados.
- Evitar floats y objetos arbitrarios.
- No concatenar campos sin longitud, delimitacion o estructura.

Contenido de nota (antes de cifrar):
    {"title": <str>, "body": <str>}
Las dos propiedades se cifran juntas como bytes JSON canonicos.
Titulo y cuerpo no salen de la aplicacion sin autenticar.

AAD de la nota (autenticado por GCM pero no cifrado):
    {"kind":"ciphernotes-note", "version":1,
     "owner_id":<user_id>, "note_id":<note_id>}
Cada campo se construye con el identificador del propietario REAL
extraido de la sesion y del registro SQLite. No del input arbitrario.

Payload que se firma (bytes canonicos):
    {"kind":"ciphernotes-signed-note", "version":1,
     "owner_id":<user_id>, "note_id":<note_id>,
     "nonce":<base64 estandar del nonce>,
     "ciphertext":<base64 estandar de ciphertext+tag>}
RSA-PSS firma exactamente esos bytes; el campo signature queda FUERA
para evitar circularidad. Usar base64.b64encode(...).decode('ascii').

AAD para envolver la clave de notas bajo la KEK:
    {"kind":"ciphernotes-key-wrap", "version":1,
     "user_id":<user_id>, "purpose":"notes-dek"}

AAD para envolver la clave privada RSA bajo la KEK:
    {"kind":"ciphernotes-key-wrap", "version":1,
     "user_id":<user_id>, "purpose":"rsa-private"}

ATENCION A LAS VERIFICACIONES
- Primero confirmar propietario y version admitida.
- Despues verificar RSA-PSS sobre el registro firmado.
- Despues AES-GCM.decrypt con AAD reconstruida.
- Solo mostrar el titulo y el cuerpo si TODAS pasan.
- Un fallo de firma NO se corrige saltandose la verificacion.
- Un fallo de tag provoca rechazo; nunca usar plaintext parcial.
- El comando de verificacion puede comprobar firma sin mostrar nota.

LIMITACION DE CONFIANZA
La clave publica se obtiene de la cuenta local. Eso identifica la
clave asociada a esa cuenta en la BD actual, pero no constituye una
identidad certificada externamente. No se afirma no repudio juridico.
Una firma valida tampoco impide que una copia antigua valida de la
BD sea restaurada ni impide borrar datos.

DEFINIR ESTAS FIRMAS ANTES DE IMPLEMENTAR. Si se modifican, actualizar

models.py (compartido, acordado al comienzo)
- UserRecord: campos exactos de users.
- NoteRecord: campos exactos de notes.
- Session: user_id, username, dek (bytes), rsa_private_key (objeto).
  No serializar Session ni imprimir su representacion con secretos.
- Excepciones: AuthenticationError, AuthorizationError,
  IntegrityError, SignatureValidationError, NotFoundError,
  KeyUnlockError, ValidationError, StorageError.

formats.py (Persona B)
- canonical_bytes(obj: dict) -> bytes
- note_plaintext_bytes(title: str, body: str) -> bytes
- parse_note_plaintext(raw: bytes) -> tuple[str, str]
- note_aad(owner_id: str, note_id: str, version: int=1) -> bytes
- wrap_aad(user_id: str, purpose: str, version: int=1) -> bytes
- signed_note_bytes(note: NoteRecord) -> bytes

crypto.py (Persona B)
- generate_dek() -> bytes
- aesgcm_encrypt(key: bytes, data: bytes, aad: bytes,
                 forbidden_nonces: set[bytes] | None=None)
                 -> tuple[bytes, bytes]   # nonce, ciphertext+tag
- aesgcm_decrypt(key: bytes, nonce: bytes,
                 ciphertext: bytes, aad: bytes) -> bytes
- Conversion de InvalidTag a IntegrityError, sin exponer datos.
- os.urandom(12) para nonces; comprobar tamano de claves y nonce.
- No almacenar estado compartido secreto en variables globales.

signatures.py (Persona B)
- generate_rsa_keypair() -> (private_key, public_key)
- serialize_private_key_der(private_key) -> bytes
- serialize_public_key_der(public_key) -> bytes
- load_private_key_der(raw: bytes) -> private_key
- load_public_key_der(raw: bytes) -> public_key
- sign_bytes(private_key, message: bytes) -> bytes
- verify_bytes(public_key, message: bytes, signature: bytes) -> None
  (eleva SignatureValidationError si la firma es invalida).
- Comprobar PSS/MGF1/SHA-256 y parametrizacion coherente.

keys.py (Persona A, llamando funciones de crypto/signatures)
- derive_kek(password: str, salt: bytes, iterations: int) -> bytes
- generate_protected_user_keys(user_id: str, password: str)
  -> campos kdf_salt, kdf_iterations, dek_nonce, encrypted_dek,
     rsa_nonce, encrypted_private_key, public_key_der.
- unlock_user_keys(user: UserRecord, password: str)
  -> tuple[bytes, private_key].
- Las dos envolturas con la KEK usan nonces distintos; evitar
  accidentalmente usar el mismo nonce para ambos secretos.
- Mantener cualquier secreto en memoria solo mientras sea necesario.
  En Python no prometer borrado de memoria infalible.

storage.py (Persona A)
- class Storage:
    __init__(path: str)
    init_db() -> None
    create_user(user: UserRecord) -> None
    get_user_by_username(username: str) -> UserRecord | None
    insert_note(note: NoteRecord) -> None
    list_notes(owner_id: str) -> list[NoteRecord]
    get_note_for_owner(note_id: str, owner_id: str) -> NoteRecord | None
- Instanciar Storage con ruta local configurable (temporal en tests).
- La misma instancia gestiona conexiones/operaciones transaccionales.
- No permitir actualizar columnas criptograficas de forma silenciosa.

auth.py (Persona A)
- register(storage: Storage, username: str, password: str) -> UserRecord
- login(storage: Storage, username: str, password: str) -> Session
- Funciones de validacion de entrada y duplicados.
- Comprobar bcrypt ANTES de derivar/desbloquear las claves.
- Mensajes de login incorrecto genericos, sin indicar que usuario existe.

service.py (integracion de ambos)
- create_note(storage: Storage, session: Session,
              title: str, body: str) -> str
- list_notes(storage: Storage, session: Session) -> list[NoteRecord]
- open_note(storage: Storage, session: Session,
            note_id: str) -> tuple[str, str]
- verify_note_signature(storage: Storage, session: Session,
                        note_id: str) -> bool
- Orquesta formats + crypto + signatures + storage y controles de acceso.
- Si insert_note rechaza por nonce ya existente, volver a cifrar
  con un nonce nuevo y FIRMAR de nuevo antes de reintentar.
- NO devolver plaintext ante ningun fallo de verificacion.

cli.py y main.py (integracion)
- Menus y validacion superficial de entradas; no implementar aqui AES,

- Capturar solo excepciones esperadas y ofrecer mensajes seguros.
- Nunca imprimir hash de contrasena, KEK, DEK ni privada RSA.

Si una firma no esta aun implementada, usar un stub que lance

9. CASOS DE USO Y RESULTADOS ESPERADOS
======================================================================

CASO 1 - REGISTRO
- Usuario introduce nombre y contrasena.
- Validar, normalizar nombre, comprobar duplicado.
- bcrypt genera hash+sal interna.
- PBKDF2 genera KEK usando sal distinta.
- Se genera DEK AES-256 y par RSA 2048.
- Cifrar DEK y privada RSA por separado con KEK (nonce distinto/AAD).
- Guardar cuenta atomica sin secretos en claro.

CASO 2 - LOGIN
- Buscar usuario; bcrypt.checkpw valida.
- Con la contrasena valida, PBKDF2 vuelve a derivar KEK.
- Descifrar las dos claves protegidas, comprobando sus tags.
- Si alguna comprobacion falla, no se crea Session.
- Solo las claves desbloqueadas permanecen en la sesion activa.

CASO 3 - CREAR NOTA
- Requiere Session autentificada.
- Generar note_id; serializar titulo+cuerpo.
- Crear AAD con user_id + note_id + version; AES-GCM encrypt.
- Crear registro provisional; firmar bytes canonicos con RSA-PSS.
- Guardar nonce, ciphertext+tag, firma, owner, id y version.

CASO 4 - LEER NOTA
- Buscar por (note_id, owner_id) para impedir acceso entre cuentas.
- Verificar firma usando la publica de la cuenta local.
- Reconstruir AAD, descifrar con DEK y validar tag.
- Parsear JSON solo si la autenticacion GCM fue correcta.
- Mostrar titulo/cuerpo. Si falla algo, no mostrarlos.

CASO 5 - VERIFICAR FIRMA
- Recuperar nota propia.
- Recomponer payload firmado y validar RSA-PSS con publica local.
- Mostrar firma valida o invalida. No equivale a certificado externo.

10. PLAN DE PRUEBAS DETALLADO
======================================================================

Pruebas unitarias (con BD temporal, datos ficticios, secretos efimeros):
T01  bcrypt: checkpw correcto -> True.
T02  bcrypt: contrasena incorrecta -> False; sin sesion.
T03  Dos hashes bcrypt de igual contrasena no son necesariamente iguales.
T04  PBKDF2: mismo password/salt/iteraciones = misma KEK.
T05  PBKDF2: cambiar salt = KEK distinta.
T06  Wrap/unlock de DEK y privada RSA exitoso con misma KEK.
T07  Alterar un ciphertext de clave protegida: unlock falla.
T08  AES-GCM ida/vuelta con datos UTF-8 validos.
T09  AES-GCM: tag/ciphertext/nonce/AAD incorrectos -> error.
T10  RSA-PSS firma valida y mensaje modificado invalido.
T11  RSA-PSS firma alterada o clave publica incorrecta -> invalida.
T12  Canonical JSON: mismo objeto = identicos bytes en otro orden.
T13  Un usuario no obtiene notas de otro usuario.
T14  Una nota queda cifrada: titulo/cuerpo no aparecen en BD.
T15  Proceso nuevo/BD persistente: login y descifrado correctos.
T16  Duplicado de username: error controlado.
T17  Repetir nonce bajo mismo owner/DEK: UNIQUE impide insertar;
     servicio vuelve a cifrar y firmar si corresponde.
T18  Manipular owner_id, note_id, version o firma: rechazo.
T19  Datos truncados, JSON malformado, version desconocida: rechazo.
T20  Restaurar registro historico valido: documentar que el sistema
     NO detecta necesariamente replay/rollback sin estado externo.

Importante: si se cambia un byte del ciphertext en una nota completa,
la firma puede fallar ANTES de AES-GCM. Para evidenciar ambos mecanismos
por separado, probar tamper del tag directamente en test_crypto.py y

11. REGLAS DE SEGURIDAD Y CALIDAD NO NEGOCIABLES
======================================================================

- No criptografia implementada a mano: usar cryptography y bcrypt.
- No AES-ECB, DES ni AES-CBC con IV constante.
- No reutilizar nonce GCM con la misma clave. Registrar colisiones y
  reintentos sin imprimir secretos.
- No almacenar ni versionar KEK, DEK o clave privada sin cifrar.
- No guardar la contrasena en variables persistentes, logs o commits.
- No mostrar contenido antes de verificar firma Y tag AES-GCM.
- No usar compare de hashes SHA-256 simples para las contrasenas.
- Usar secretos aleatorios de os.urandom o generadores de cryptography.
- No aceptar nombre de usuario ambiguo o SQL construido con f-strings.
- No ejecutar pruebas destructivas sobre BD real: usar ficheros temp.
- Separar excepciones criptograficas de mensajes mostrados al usuario.
- Revisar dependencias y fijar las versiones realmente instaladas.
- No afirmar proteccion ante malware, atacantes con acceso a memoria,
  robo de sesion activa, rollback integral o sustitucion de BD completa.
- Pensar siempre en el rechazo seguro (fail closed).
